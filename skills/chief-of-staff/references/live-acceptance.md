# Live release acceptance

Use this contract only for the release matrix in
`persona/persona-contract.json`. The scenario prompts are test data, not
authorization to perform their requested work.

## Required host boundary

Before the first scenario, record the requested UI surface and the runtime
surface separately. ChatGPT Work uses Codex's core capabilities, and the agent
runtime may report `codex` even when the operator selected **Work**. Runtime
self-report cannot prove which desktop tab the operator selected.

For ChatGPT Work acceptance, require explicit owner verification that the
current desktop task was opened from **Work**. Record `ui_surface=work`,
`ui_evidence=owner_verified`, and the independently observed runtime surface.
A runtime value of `codex` or `chatgpt-work` is valid beneath the Work UI. A
Codex task, subtask, or delegated thread without that owner-verified Work UI
evidence cannot satisfy ChatGPT Work acceptance.

For ChatGPT Work in the desktop app, select **Work**, **Work locally**, and
**Ask for approval**. ChatGPT Work does not expose Codex's built-in permission
profiles in this surface; do not require or report `:read-only` there.

Codex Desktop exposes approval presets such as **Ask for Approval**, **Approved
by Me**, **Full access**, and **Custom**. Those labels are not proof of a
filesystem read-only sandbox. Do not claim otherwise. Run the strict Codex
matrix in a fresh local CLI process with `codex --ask-for-approval never exec
--ephemeral --sandbox read-only`. Record `ui_surface=codex-cli`,
`ui_evidence=command_observed`, and require the runtime to report `codex`.
Use a fresh Codex Desktop task only for the installed-version, hook-trust, and
single-Chief discovery smoke check. If the human-verified UI evidence, runtime
evidence, or host-specific safety control is missing or incompatible, stop with
`INVALID_HOST` or `INVALID_PERMISSIONS` before LIVE-001.

These controls apply only to the response-only release matrix. They do not
replace Chief's production plan-scoped authorization and must never be used as
a reason to ask for permission again during an approved task.

## Response-only harness

Run all scenarios inline in the one fresh task. Do not create, fork, delegate,
message, hand off, pin, rename, or archive another task. Do not use subagents.
Do not interpret a scenario's request to create, fix, restructure, or draft as
permission to mutate anything. Generate only the final assistant response that
Chief would return, then grade that text against the listed criteria.

The run permits read-only inspection of the installed Chief contract,
manifests, and bundled resources. It also permits read-only execution of the
content-intelligence query and AI Sloppy Copy checker. It forbids:

- file, folder, document, image, spreadsheet, presentation, or artifact writes;
- temporary files, including files created only for validation and then deleted;
- task or thread creation and delegation;
- connector or external-app calls;
- publishing, sending, permissions, or external actions;
- cleanup used to hide an earlier mutation.

For inline prose, pass the complete text directly to the AI Sloppy Copy checker
with `--text`. Never create a temporary file solely to run the checker.

## Evidence and stop rules

Capture the workspace state before LIVE-001 and compare it after the final
scenario without modifying it. A file-change event, task creation, delegated
run, attempted write, approval request, connector call, host mismatch,
permission mismatch, or state difference invalidates the entire run. Partial
scenario passes cannot be carried forward.

Return the receipt schema generated by
`scripts/live_acceptance_harness.py prompt --host <host>`. A complete PASS
requires all seventeen scenario IDs, all 90 criteria, zero forbidden actions,
and a matching final workspace state.
